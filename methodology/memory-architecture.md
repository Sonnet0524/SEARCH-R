# 记忆分层架构
> 三层记忆系统：即时层 + 近中期层 + 长期层

**版本**: v2.1 | **日期**: 2026-08-14

---

## 为什么需要记忆分层？

### 问题

AI Agent 面临一个根本矛盾：
- **上下文窗口有限**：每次对话能加载的信息有上限
- **知识积累无限**：长期研究中产出的知识越来越多

如果试图把所有知识都塞进上下文：
- 上下文爆满，核心规则反而被稀释
- 每次对话都要重新加载大量历史，效率极低
- 关键信息被淹没在噪声中

如果不加载历史：
- 每次对话都像重新开始
- 重复研究已经研究过的问题
- 无法积累和进化

### 方案

三层记忆架构——像人类记忆一样分层管理：

```
即时层（工作台）
├── 容量：≤5KB
├── 内容：规则 + 状态锚点 + 指针
├── 特点：每次对话自动加载
└── 类比：你工作时摆在桌上的东西

近中期层（文件柜）
├── 容量：按需
├── 内容：索引 + 条目
├── 特点：按需读取，主动更新
└── 类比：你身后的文件柜，需要时转身取

长期层（图书馆）
├── 容量：无限
├── 内容：全部历史对话的详细记录
├── 特点：语义检索，按需召回
└── 类比：城市的图书馆，需要时去查阅
```

---

## 即时层（≤5KB）

### 设计原则

即时层是 Agent 的"工作台"——每次对话都会加载，因此必须精简到极致。

**容量硬限制**：≤ 5KB（约 1500 个汉字）

**只放三类东西**：
1. **规则**：必须遵守的行为准则
2. **状态锚点**：当前状态的关键指针
3. **指针**：指向近中期层和长期层的引用

### 即时层组成

#### soul（身份定义）
**内容**：Agent 的身份、核心信念、行为边界
**容量目标**：≤ 1KB

#### user（用户画像）
**内容**：用户的基本信息、偏好、工作风格
**容量目标**：≤ 0.5KB

#### memory（规则 + 锚点 + 指针）
**内容**：核心规则、当前状态锚点、指向其他记忆层的指针
**容量目标**：≤ 2KB

#### tools（工具经验索引）
**内容**：工具使用的经验和注意事项的索引
**容量目标**：≤ 0.5KB

#### secret（敏感凭证）
**内容**：API Key、密码等敏感信息的引用
**容量目标**：≤ 0.5KB

### 即时层写入规则

1. **每次对话开始时自动加载**：所有即时层内容
2. **写入前检查容量**：超出 5KB 时必须精简
3. **精简策略**：
   - 删除过时信息
   - 将详细内容移入近中期层，只保留指针
   - 合并重复规则
4. **规则变更时更新**：新规则加入，旧规则移除

---

## 近中期层

### 设计原则

近中期层是 Agent 的"文件柜"——存放当前活跃的信息，按需读取。

**组织方式**：索引 + 条目

**核心文件**：
- `recent_memory/index.json` — 全量目录
- `recent_memory/project/*.md` — 项目进度快照
- `recent_memory/decision/*.md` — 决策记录
- `recent_memory/todo/*.md` — 待办事项

### index.json 结构

```json
{
  "version": "2.0",
  "last_updated": "2026-08-14",
  "entries": [
    {
      "file": "project/topic-a.md",
      "type": "project",
      "summary": "课题A：Agent记忆系统。当前Analyze阶段，已产出3个Insight",
      "tags": ["agent", "memory", "active"],
      "created": "2026-07-01",
      "updated": "2026-08-14",
      "last_referenced": "2026-08-14"
    }
  ]
}
```

> **v2.1 新增**：`last_referenced` 字段，用于记忆健康度自检时识别"僵尸"条目。每次读取或引用该条目时更新此字段。

### 条目类型

#### project/*.md — 项目进度快照
#### decision/*.md — 决策记录
#### todo/*.md — 待办事项

### 近中期层读写规则

1. **按需读取**：根据 index.json 的摘要判断是否需要读取具体条目
2. **主动更新**：状态变化时立即更新对应条目
3. **引用追踪**：每次读取条目时，同步更新 `last_referenced` 日期
4. **定期清理**：完成的 todo 标记完成，过时的 project 标记归档
5. **容量管理**：单个条目不超过 2KB，超出则拆分或归档

---

## 长期层

### 设计原则

长期层是 Agent 的"图书馆"——存放全部历史对话的详细记录，通过语义检索访问。

### 检索策略

```
1. 先查即时层（已自动加载）
   ↓ 没有找到
2. 查近中期层（读 index.json，按摘要定位）
   ↓ 没有找到
3. 查长期层（语义检索 memory_search）
   ↓ 
4. 如果找到有价值的信息
   → 判断是否需要提升到近中期层
   → 或者只是临时参考
```

### 沉淀规则

1. **近中期层 → 长期层**：完成的课题、过时的决策，从近中期层归档到长期层
2. **长期层 → 近中期层**：如果长期层的信息重新变得相关，提升到近中期层
3. **即时层 → 近中期层**：详细内容从即时层下沉到近中期层，即时层只保留指针

## 记忆流转全景

```
                    ┌──────────────────┐
                    │     长期层        │
                    │  (语义检索)       │
                    │  全部历史记录     │
                    └────────┬─────────┘
                             │
                    沉淀 ↓    ↑ 提升
                             │
                    ┌────────┴─────────┐
                    │    近中期层       │
                    │  (索引+条目)      │
                    │  当前活跃信息     │
                    └────────┬─────────┘
                             │
                    精简 ↓    ↑ 加载
                             │
                    ┌────────┴─────────┐
                    │    即时层         │
                    │  (≤5KB)          │
                    │  规则+锚点+指针   │
                    └──────────────────┘
```

## 记忆容量控制

### 各级容量指南

| 层级 | 容量 | 控制策略 |
|------|------|----------|
| 即时层 | ≤ 5KB | 硬限制，超出必须精简 |
| 近中期层 index.json | ≤ 50 条目 | 超出时归档已完成条目 |
| 近中期层单个条目 | ≤ 2KB | 超出时拆分或精简 |
| 长期层 | 无限 | 无需控制 |

## 记忆智能化管理（v2.1 新增）

### 设计动机

v2.0 的记忆管理依赖人工判断"什么时候该归档、什么时候该提升"。v2.1 引入规则驱动的自动化决策，让 Agent 能自主管理记忆生命周期。

### 规则 1：跨课题引用提升

**触发条件**：一条 Insight 被 ≥2 个不同课题引用

**决策**：将该 Insight 提升为**跨课题 Insight**

**执行步骤**：
1. 在 Insight 记录中标注 `cross_topic: true`
2. 在 `insights_index.md` 中标注关联的课题列表
3. 在课题网络图中添加对应的跨课题连接边
4. 通知 Human（如果此前未确认过跨课题关联）

**示例**：
```markdown
### Insight #015: 记忆分层原则
- cross_topic: true
- 引用课题：[Agent记忆系统, 上下文管理, 知识图谱管理]
- 原始课题：Agent记忆系统
```

### 规则 2：僵尸条目降级

**触发条件**：近中期层条目 30 天内未被任何会话引用（`last_referenced` 超过 30 天）

**决策**：标记为"待归档"，在下次课题网络梳理时批量处理

**执行步骤**：
1. 课题网络梳理时扫描 `index.json` 中所有条目的 `last_referenced`
2. 30 天未引用的条目标记为 `status: "stale"`
3. 列出待归档清单，由 Human 确认（或直接归档已完成类型的条目）
4. 归档操作：从 index.json 移除，条目文件保留但标记 `archived: true`

**注意**：
- `type: "project"` 且状态为 active 的条目不参与僵尸检测
- `type: "todo"` 且有未完成任务的条目不参与僵尸检测

### 规则 3：新增 Insight 冗余检查

**触发条件**：每次写入新 Insight 前

**执行步骤**：
1. 读取 `insights_index.md` 中已有的 Insight 列表
2. 对新 Insight 与已有 Insight 做语义对比
3. 判断结果：
   - **完全重复**：不写入，引用已有 Insight
   - **部分重叠**：写入新 Insight，但标注与哪个 Insight 重叠，以及差异点
   - **矛盾**：写入新 Insight，标注矛盾关系，触发冲突解决流程
   - **无关联**：正常写入

**冗余检查记录格式**：
```markdown
### 冗余检查 [日期]
- 新 Insight：[标题]
- 对比结果：无关联 / 部分重叠 #XXX / 矛盾 #XXX / 完全重复 #XXX
- 处理：正常写入 / 合并 / 冲突解决
```

### 规则 4：引用追踪与图谱

**机制**：每次写入或引用 Insight 时，在 Insight 记录中更新引用信息

**Insight 记录新增字段**：
```markdown
- **引用记录**：
  - [2026-08-10] 课题A Analyze 阶段引用
  - [2026-08-12] 课题C Explore 阶段引用
  - [2026-08-14] 课题网络梳理时确认为跨课题 Insight
```

**引用图谱维护**：
- 在 `insights_index.md` 末尾维护一个简单的引用统计表
- 格式：`Insight #XXX | 引用次数: N | 引用课题: [A, B, C] | 最后引用: YYYY-MM-DD`
- 此表在每次 Insight 被引用时更新

### 记忆健康度自检（集成到课题网络梳理）

在每次课题网络梳理（每 1-2 周）时，同步执行以下检查：

1. **僵尸条目扫描**：检查 index.json 中 last_referenced 超过 30 天的条目
2. **Insight 引用统计**：检查 insights_index.md 中引用次数为 0 的 Insight
3. **跨课题连接完整性**：检查所有 cross_topic Insight 是否已在网络图中体现
4. **容量健康度**：
   - index.json 条目数 / 50 → 健康（<60%）/ 警告（60-80%）/ 危险（>80%）
   - 即时层字节数 / 5KB → 同上

**健康度报告格式**（集成到网络梳理输出）：
```markdown
## 记忆健康度
- 近中期层：X/50 条目（健康）
- 僵尸条目：Y 个（建议归档）
- 零引用 Insight：Z 个（需评估价值）
- 跨课题 Insight：W 个（网络图已更新/待更新）
```

## 实践指南

### 何时写入哪一层？

| 场景 | 写入层级 | 示例 |
|------|----------|------|
| 发现新规则 | 即时层 memory | "活跃课题不超过 2 个" |
| 课题状态变化 | 近中期层 project/ | "课题 A 进入 Analyze 阶段" |
| 做出重要决策 | 近中期层 decision/ | "选择三层记忆架构" |
| 新增待办 | 近中期层 todo/ | "完成 Insight 提炼" |
| 历史对话记录 | 长期层 | 自动存储 |
| 课题完成 | 近中期层 → 长期层 | 从 project/ 归档到长期层 |
| Insight 被多课题引用 | 近中期层 + 图谱更新 | 标注 cross_topic，更新引用记录 |

### 常见问题

**Q: 即时层 5KB 够不够用？**
A: 够。即时层只放规则、锚点和指针，不放详细内容。详细内容在近中期层。

**Q: 如果忘记了近中期层的内容怎么办？**
A: index.json 有每个条目的摘要。先看摘要，判断是否需要读取详细内容。

**Q: 长期层的语义检索准确吗？**
A: 取决于查询质量。查询越具体，检索越准确。建议先尝试即时层和近中期层。

**Q: 僵尸条目会不会误删有用信息？**
A: 不会直接删除。僵尸检测只标记 `stale`，归档需要 Human 确认（或仅对已完成类型的条目自动归档）。文件本身保留。

**Q: 引用追踪会不会增加太多负担？**
A: 不会。引用追踪只在写入或读取 Insight 时执行，是一行记录的追加，不涉及额外搜索。
