# 洞察管理体系
> 三层知识结构 + 洞见判定标准 + 跨课题关联发现

**版本**: v2.1 | **日期**: 2026-08-14

---

## 为什么需要洞察管理？

### 问题

传统研究产出是一堆文件：观察笔记、检索报告、理论文档、反思笔记。但面对这些文件，我们经常遇到：
- "这个发现到底是信息、数据还是洞见？"
- "之前的研究明明得出了一个重要结论，但现在找不到了。"
- "两个课题各自有发现，但没人注意到它们其实说的是同一件事。"

### 根因

v1.x 的文档模板体系解决了"记录"的问题，但没有解决"分类"和"发现"的问题。

### 方案

洞察管理体系提供三个能力：
1. **三层分类**：Info → Data → Insight，让每个发现有明确的知识层级
2. **洞见判定**：唯一判据"能否改变行动逻辑"，让洞见和噪声分离
3. **关联发现**：跨课题关联检查，让孤岛式的发现形成网络

## 三层知识结构

### 概览

```
Info（信息）
├── 事实、数据点、观察记录
├── 来源明确，未经验证
├── 量大，价值密度低
└── 示例："GPT-4 有 1.8 万亿参数"

Data（数据）
├── 经过整理的结构化信息
├── 已分类、已关联、已验证来源
├── 量中等，价值密度中等
└── 示例："参数量与推理能力的对比表格（10个模型）"

Insight（洞见）
├── 能改变行动逻辑的发现
├── 经过验证和 Human 评审
├── 量少，价值密度高
└── 示例："参数量超过阈值后，推理能力的提升来自架构而非规模"
```

### 各层详解

#### Info（信息）
**是什么**：原始的事实、数据点、观察记录
**特征**：来源明确、未经整理、可能有价值但尚未证明
**存储位置**：`observations/`、`retrievals/`

#### Data（数据）
**是什么**：经过整理的结构化信息
**特征**：已从 Info 整理而来、有结构、来源已验证
**存储位置**：`retrievals/`（整理后的检索报告）、`theory/`（分析数据）

#### Insight（洞见）
**是什么**：能改变行动逻辑的发现
**特征**：从 Data 提炼而来、通过了洞见判定、经过验证和 Human 评审
**存储位置**：`theory/`（理论文档）、`insights_index.md`（索引）

## 洞见判定标准

### 唯一判据

> **能否改变行动逻辑？**

这是判断一个发现是否为 Insight 的**唯一**标准。

### 判定流程

```
一个发现
  ↓
问自己：如果知道了这个发现，我的下一步行动会不同吗？
  ↓
├── 会不同 → 这是 Insight
│   └── 问：改变了什么行动？→ 记录行动含义
│
└── 不会不同 → 这不是 Insight
    └── 问：那它是什么？→ 降级为 Data 或 Info
```

### 不合格洞见的类型

| 类型 | 特征 | 示例 |
|------|------|------|
| 数据点 | 只是一个事实或数字 | "API 响应时间 200ms" |
| 过程结论 | 研究过程中的决策记录 | "我们决定先研究 A" |
| 工程设计 | 具体技术方案，未抽象为方法论 | "用 Redis 做缓存" |
| 通识 | 大家都知道的事情 | "AI 正在改变世界" |

## 洞察索引管理

### insights_index.md 结构

```markdown
# 洞察索引
> 所有 Insight 的全量索引。唯一判据：能否改变行动逻辑。

## 统计
- 总 Insight 数：X
- 本周期新增：Y
- 跨课题关联：Z

## Insight 列表

### Insight #001: [标题]
- **内容**：[一句话描述]
- **来源**：[课题名称] + [具体文档]
- **验证状态**：Candidate / Confirmed / Refuted
- **行动含义**：[知道这个后，什么行动会不同？]
- **适用范围**：[在什么条件下成立？]
- **关联 Insight**：[#003（补充）, #007（矛盾）]
- **cross_topic**：true / false（v2.1 新增）
- **引用记录**：（v2.1 新增）
  - [YYYY-MM-DD] 课题X [阶段] 引用
- **创建日期**：YYYY-MM-DD
- **最后更新**：YYYY-MM-DD
```

### 验证状态

| 状态 | 含义 | 下一步 |
|------|------|--------|
| **Candidate** | 候选洞见，尚未经过验证 | 进入 Review → Confirm 流程 |
| **Confirmed** | 已验证的洞见 | 正式归档，可被其他课题引用 |
| **Refuted** | 被证伪的洞见 | 保留记录，标注证伪原因 |

### 引用统计表（v2.1 新增）

在 insights_index.md 末尾维护：

```markdown
## 引用统计
| Insight | 引用次数 | 引用课题 | 最后引用 |
|---------|---------|---------|---------|
| #001 记忆分层原则 | 3 | A, B, C | 2026-08-14 |
| #002 上下文管理策略 | 1 | A | 2026-08-10 |
```

## 跨课题关联发现机制

### 关联类型

| 类型 | 说明 | 示例 |
|------|------|------|
| **补充** | Insight A 补充了 Insight B 的适用范围 | "记忆分层原则"补充了"上下文管理策略" |
| **矛盾** | Insight A 与 Insight B 矛盾 | "主动遗忘"与"完整记录"矛盾 |
| **增强** | Insight A 为 Insight B 提供了额外证据 | 新研究证实了旧 Insight |
| **衍生** | Insight A 引发了新的研究问题 | 从"记忆分层"衍生出"分层边界如何确定" |

## 实时关联发现（v2.1 新增）

### 设计动机

传统做法是每 1-2 周做一次课题网络梳理来发现跨课题关联。但 Insight 产出时如果只做记录不做关联检查，可能错过即时发现的窗口。

**问题**：每次 Insight 产出时做全量扫描消耗太大（需要读取所有课题的 Insight 索引）。

**方案**：轻量级局部匹配——只在 Insight 产出时做最小化关联检查，积累线索后在网络梳理时批量验证。

### 执行流程

```
1. 产出新 Insight
   ↓
2. 提取 2-3 个关键词标签（从 Insight 的核心概念中提取）
   ↓
3. 读取 research/课题总览.md（已有的 33 课题索引，约 2-3KB）
   ↓
4. 在课题索引中做关键词匹配，找出 1-3 个可能相关的课题
   ↓
5. 如果匹配到相关课题：
   ├── 在新 Insight 记录中标注：potential_links: [课题X, 课题Y]
   ├── 在 insights_index.md 的引用统计中标注潜在关联
   └── 不立即深入分析（避免消耗过大）
   ↓
6. 如果未匹配到：正常记录，不额外操作
   ↓
7. 等待定期课题网络梳理时，批量验证所有 potential_links
```

### 关键词标签提取规则

从 Insight 中提取最能代表其核心概念的 2-3 个关键词：
- 优先提取名词性概念（如"记忆分层"、"上下文管理"）
- 避免过于宽泛的词（如"系统"、"方法"、"优化"）
- 避免过于具体的词（如某个特定工具的名称）

### 效果验证机制

为判断实时关联发现是否有效，需要记录以下数据：

**验证日志**（保存在 `research/search-r-meta/realtime-link-log.md`）：
```markdown
## 实时关联发现日志

### [日期] [Insight 编号]
- 关键词标签：[tag1, tag2, tag3]
- 匹配到的课题：[课题X, 课题Y]
- 网络梳理验证结果：
  - [ ] 确认为有效关联（补充/矛盾/增强/衍生）
  - [ ] 误报（关键词重合但无实际关联）
  - [ ] 待验证
```

**效果评估指标**：
- **命中率**：网络梳理验证后确认为有效关联的比例
- **覆盖率**：实时发现 + 网络梳理发现 vs 仅网络梳理发现（对比是否有新增）
- **平均消耗**：每次 Insight 产出时的额外匹配耗时（目标：<30 秒）

**评估周期**：每 4 周评估一次，如果命中率 <30%，调整关键词提取规则或放弃此机制。

### 成本分析

| 步骤 | 操作 | 预估消耗 |
|------|------|---------|
| 提取关键词 | 从 Insight 文本中提取 | 极低（思维过程） |
| 读取课题索引 | 读 research/课题总览.md | 低（~3KB 文件） |
| 关键词匹配 | 文本匹配 | 极低 |
| 写入标注 | 更新 Insight 记录 | 低 |
| **总计** | | **~10-20 秒额外耗时** |

对比：全量扫描（读取所有课题的 Insight 索引）预估需要 3-5 分钟。

## 实践指南

### 何时进行洞察管理？

| 时机 | 动作 |
|------|------|
| 每次研究产出后 | 识别候选 Insight |
| Insight 产出时（v2.1） | 提取关键词，做轻量级关联匹配 |
| Harvest 阶段 | 正式提炼和归档 Insight |
| Reflect 阶段 | 检查洞察索引一致性 |
| 课题网络梳理 | 验证 potential_links，发现跨课题关联 |
| 新课题启动 | 检索已有 Insight 避免重复 |
