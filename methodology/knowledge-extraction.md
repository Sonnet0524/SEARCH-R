# 知识萃取协议

> 从研究课题中系统性萃取知识，按 Info/Data/Insight 三层分类

**版本**: v2.0 | **日期**: 2026-08-14

---

## 为什么需要知识萃取协议？

### 问题

研究过程中会产出大量内容：观察笔记、检索报告、理论文档、反思笔记。但这些内容往往：
- 停留在单个课题内部，不被其他课题复用
- 混杂着 Info、Data 和 Insight，没有分层
- 随着课题归档，其中的洞见被一起"埋掉"

### 根因

v1.x 的 SEARCH-R 循环专注于"研究过程"，没有定义"知识产出"的标准化流程。

### 方案

知识萃取协议——在 SEARCH-R 各阶段嵌入知识萃取动作，确保：
1. 每个研究产出都被分类（Info/Data/Insight）
2. 有价值的洞见被提取并归档
3. 跨课题关联被发现和维护

## 萃取流程

### 总体流程

```
研究产出（观察/检索/理论/反思）
  ↓
步骤 1：识别知识候选
  ↓
步骤 2：三层分类（Info/Data/Insight）
  ↓
步骤 3：判断是否达到 Insight 级别
  ↓
步骤 4：写入洞察索引
  ↓
步骤 5：检查跨课题关联
  ↓
步骤 6：更新知识图谱
```

### 步骤详解

#### 步骤 1：识别知识候选

**做什么**：从研究产出中识别可能包含知识的内容片段

**方法**：
- 扫描研究产出，标记以下类型的内容：
  - 事实性陈述（→ Info 候选）
  - 对比/分析/总结（→ Data 候选）
  - 原则/规律/洞见（→ Insight 候选）

**示例**：
```
从一篇观察笔记中识别出：
- "GPT-4 在 50K token 时准确率下降 30%" → Info 候选
- "5 个模型在不同上下文长度的表现对比" → Data 候选
- "上下文管理的关键不是压缩，而是分层" → Insight 候选
```

#### 步骤 2：三层分类

**做什么**：将每个候选归入 Info / Data / Insight 层级

**分类标准**：

| 层级 | 标准 | 处理方式 |
|------|------|----------|
| Info | 原始事实，未分析 | 记录来源，存入 observations/ |
| Data | 已整理的结构化信息 | 建立关联，存入 retrievals/ |
| Insight | 能改变行动逻辑 | 进入 Insight 判定流程 |

#### 步骤 3：Insight 判定

**做什么**：用唯一判据判断候选是否为真正的 Insight

**判据**：能否改变行动逻辑？

```
候选 Insight："上下文管理的关键不是压缩，而是分层"
  ↓
问：如果知道了这个，我的下一步行动会不同吗？
  ↓
答：会。设计记忆系统时，不再追求压缩算法，
   而是设计分层架构。
  ↓
判定：✅ 这是 Insight
```

**不是 Insight 的降级处理**：
```
候选 Insight："GPT-4 有 1.8T 参数"
  ↓
问：知道了这个，我的下一步行动会不同吗？
  ↓
答：不会。这个信息不改变任何设计决策。
  ↓
判定：❌ 降级为 Info
```

#### 步骤 4：写入洞察索引

**做什么**：将通过判定的 Insight 写入 insights_index.md

**格式**：
```markdown
### Insight #XXX: [标题]
- **内容**：[一句话描述]
- **来源**：[课题名称] + [具体文档]
- **验证状态**：Candidate
- **行动含义**：[知道后什么行动会不同]
- **适用范围**：[在什么条件下成立]
- **关联 Insight**：[暂无 / 列出关联]
- **创建日期**：YYYY-MM-DD
```

#### 步骤 5：检查跨课题关联

**做什么**：检查新 Insight 是否与其他课题的 Insight 有关联

**检查方法**：
1. 在洞察索引中搜索语义相关的 Insight
2. 判断关联类型（补充/矛盾/增强/衍生）
3. 记录关联关系

**关联类型**：

| 类型 | 说明 | 动作 |
|------|------|------|
| 补充 | 补充了另一个 Insight 的适用范围 | 在双方标注关联 |
| 矛盾 | 与另一个 Insight 矛盾 | 触发冲突解决 |
| 增强 | 提供了额外证据 | 增强置信度 |
| 衍生 | 引发了新的研究问题 | 创建新研究条目 |

#### 步骤 6：更新知识图谱

**做什么**：更新 Insight 之间的关系图

**输出**：更新洞察索引中的关联关系，更新课题网络图

## SEARCH-R 各阶段的知识萃取

### S - Survey 阶段

**萃取重点**：检索已有知识，避免重复

| 动作 | 说明 |
|------|------|
| 检索已有 Insight | 在开始新研究前，检查是否已有相关 Insight |
| 标记知识缺口 | 明确哪些问题没有现成 Insight |
| 复用已有 Insight | 如果已有 Insight 覆盖当前问题，直接引用 |

**示例**：
```
Survey 阶段发现："Agent 记忆管理"是研究问题
  ↓
检索洞察索引：已有 Insight #015（记忆分层原则）
  ↓
判断：Insight #015 部分覆盖，但缺少"分层边界"的讨论
  ↓
标记：知识缺口 = "分层边界的确定方法"
```

### E - Explore 阶段

**萃取重点**：萃取新发现的信息

| 动作 | 说明 |
|------|------|
| 萃取 Info | 从检索结果中识别新的 Info |
| 整理为 Data | 将 Info 整理为结构化的 Data |
| 标注来源 | 每个 Info/Data 都记录来源 |

### A - Analyze 阶段

**萃取重点**：Data → Insight 提炼

| 动作 | 说明 |
|------|------|
| 提炼 Insight | 从 Data 中提炼能改变行动逻辑的发现 |
| Insight 判定 | 用唯一判据检验 |
| 过滤不合格洞见 | 降级不是 Insight 的发现 |

### R - Review 阶段

**萃取重点**：验证 Insight

| 动作 | 说明 |
|------|------|
| Human 验证 | 让 Human 验证 Insight 是否站得住脚 |
| 修订 Insight | 根据反馈修订 |
| 确认状态 | Candidate → Confirmed / Refuted |

### C - Confirm 阶段

**萃取重点**：实践检验 Insight

| 动作 | 说明 |
|------|------|
| 实践检验 | 将 Insight 应用到实际场景 |
| 收集反例 | 有意寻找反例 |
| 更新置信度 | 根据验证结果更新 |

### H - Harvest 阶段

**萃取重点**：正式归档 + 跨课题关联

| 动作 | 说明 |
|------|------|
| 🔑 洞见提炼 | 正式从本轮研究中提炼 Insight |
| 写入洞察索引 | 新 Insight 正式写入 |
| 跨课题关联检查 | 检查对其他课题的影响 |
| 触发级联更新 | 影响其他课题时触发更新 |

### R - Reflect 阶段

**萃取重点**：评估对知识体系的影响

| 动作 | 说明 |
|------|------|
| 课题网络影响评估 | 评估本轮对课题网络的影响 |
| 知识图谱更新 | 更新 Insight 间的关系 |
| 下一步优先级 | 基于知识图谱决定下一步 |

## 知识应用协议

### 原则

知识不是用来"存"的，是用来"用"的。

### 各阶段如何与已有知识交互

| 阶段 | 交互方式 | 示例 |
|------|----------|------|
| Survey | **检索**：查询已有 Insight 避免重复 | "查一下之前关于 X 的 Insight" |
| Explore | **对比**：将新 Info 与已有 Data 对比 | "新数据和之前的 Data #3 一致/矛盾" |
| Analyze | **构建**：基于已有 Insight 构建新理论 | "在 Insight #5 的基础上，进一步..." |
| Review | **验证**：用已有 Insight 检验新 Insight | "新 Insight 和 Insight #8 是否一致？" |
| Confirm | **检验**：在已有 Insight 的指导下设计验证 | "按 Insight #5 的原则，验证方案应该是..." |
| Harvest | **关联**：将新 Insight 与已有 Insight 关联 | "新 Insight 补充了 Insight #3" |
| Reflect | **评估**：评估新 Insight 对整体知识体系的影响 | "新 Insight 让知识网络更紧密了" |

## 实践指南

### 什么时候做知识萃取？

| 时机 | 萃取深度 | 说明 |
|------|----------|------|
| 每次研究产出后 | 轻量 | 快速识别候选，不深入处理 |
| Harvest 阶段 | 完整 | 正式的 Insight 提炼和归档 |
| 课题网络梳理 | 全局 | 检查跨课题关联和知识图谱 |
| 新课题启动 | 检索 | 检查已有知识避免重复 |

### 知识萃取的检查清单

- [ ] 是否从研究产出中识别了知识候选？
- [ ] 是否按 Info/Data/Insight 三层分类？
- [ ] Insight 是否通过了"能否改变行动逻辑"判定？
- [ ] 正式 Insight 是否写入洞察索引？
- [ ] 是否检查了跨课题关联？
- [ ] 知识图谱是否更新？

### 常见问题

**Q: 每次研究都要做完整的知识萃取吗？**
A: 不需要。轻量研究（如快速信息查询）只需在 Harvest 阶段做简单检查。完整的萃取流程适用于正式的研究循环。

**Q: 知识萃取会不会很耗时？**
A: 如果嵌入到 SEARCH-R 各阶段中，不会额外增加太多时间。关键是 Harvest 阶段的完整萃取（约 5-10 分钟）。

**Q: 如何处理矛盾的知识？**
A: 矛盾不是坏事。它可能意味着：
- 适用范围不同
- 需要更高层次的理论
- 其中一个需要修正
标记矛盾，在 Reflect 阶段处理。
